# ResourceGrab 手机版方案对比

> 基于对当前源码的实地核对（`src/ResourceGrab.Core` 192 文件 / 24,785 行，`src/ResourceGrab.App` 193 文件 / 38,278 行）。
> 结论不是"用哪个框架"，而是"先决定手机在什么位置"。

## 1. 结论先行

| 判断 | 依据 |
| --- | --- |
| **Core 是资产，App 是负债** | `Core` 用 `net10.0`，只有 4 处 Windows 依赖且都带 `IsWindows()` 守卫，24.8k 行源适配/下载/解析逻辑可在手机上原样跑 |
| **WPF 界面基本不能搬** | 36 个视图、64 个 `.xaml.cs`、仅 6 个 ViewModel；`WindowChrome` 21 处、`DWM` 5 处、动画 180 处、`FlyleafHost` 19 处——全是 WPF/Windows 私有 |
| **不是"移植"，是"重做界面 + 复用内核"** | 手机端信息架构本来就要重排（左栏 216px + 右筛栏 300–440px 的桌面骨架没有对应物） |
| **分发是硬约束** | 内容是 18+（JM / MissAV / JavDB），Google Play 与 App Store 都过不了审；只能侧载 APK / PWA / 自签 |

## 2. 现状盘点

### 可直接复用（Core）

| 模块 | 行数 | 移植成本 |
| --- | --- | --- |
| `Sources/` 源适配（签名、解密、HTML 解析） | 6,471 | 低：纯 HttpClient + AngleSharp |
| `Downloading/` 下载引擎（Channel + 按源限流 + 断点续传） | 713 | 低：纯 BCL |
| `Services/` 业务（库、刮削、阅读、配置、日志） | 14,606 | 中：见 §6 的平台适配点 |
| `Models/` `Http/` `Utils/` | 2,534 | 低 |
| `Themes/Tokens.xaml` `Colors.xaml` `DarkColors.xaml` | — | 中：令牌可逐条翻译成目标框架的资源字典 |

### 必须重做（App）

- 36 个 `Views/*.xaml` + 47 个 `Controls` + 10 个 `Dialogs`
- `MainWindow.xaml.cs`（82KB 上帝对象）里的缓存、LRU、主题切换、对话框编排
- 桌面专属：`DwmSetWindowAttribute`、`WindowChrome`、`System.Windows.Media.Animation`、Flyleaf 播放器

### 还没搬就已经挡路的架构债

只有 6 个 ViewModel 配 64 个代码后置文件，说明**排版逻辑和业务逻辑焊在一起**。
换壳时这段既不能直接编译、也不能直接翻译。建议移植前先把高频页（搜索 / 详情 / 阅读器 / 下载队列）
抽成 `ViewModel + 命令`，让 Avalonia 与 MAUI 都能直接吃。

## 3. 方案对比

工作量按「单人、熟悉现有代码、只做手机 MVP」估算。

| # | 方案 | UI 复用 | Core 复用 | 工作量 | 交付形态 | 主要风险 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 桌面端加 HTTP API + 手机 PWA | 0（重写，但令牌可借） | ~95%（Core 跑在电脑上） | **2–4 周** | 浏览器 / 可安装 PWA | 电脑必须开机；手机不能离线自存 |
| 2 | **Avalonia 11 + .NET for Android** | 令牌 + 部分 C# 逻辑 | 80–90% | **6–10 周** | 独立 APK（iOS 同一套 XAML） | TLS 指纹、ffmpeg、播放器、后台下载 |
| 3 | MAUI + Blazor Hybrid（Razor 一套 UI） | 0，但一套 UI 可同时出 Web 版 | ~85% | **5–8 周** | APK + iOS App | WebView 上长列表/图片墙性能；播放器需原生 handler |
| 4 | 原生 Kotlin/Compose（或 Swift）重写 | 0 | 0（24.8k 行解析逻辑要移植） | **3 个月+** | APK，体验最好 | 双份代码维护，源站改版要改两处 |
| 5 | 桌面为主 + 手机薄客户端（只做遥控 / 阅读） | 0 | ~60% | **3–5 周** | APK 或 PWA | 功能受限，本质是配套工具 |

## 4. 逐个展开

### 方案 1：桌面当服务端 + 手机 PWA（最快见效）

```
手机浏览器 ──HTTP──▶ ASP.NET Core Minimal API（进程内 / 独立 exe）
                          └─▶ 复用 ResourceGrab.Core（一行不改）
```

- **做法**：把 Core 的服务包一层 `Endpoints`（搜索 / 详情 / 章节图 / 阅读 / 播放地址 / 下载入队 / 进度 SSE），
  UI 用 React/Vue 做响应式：底部 Tab（发现 / 书架 / 下载 / 我的）、卡片流、全屏阅读器。
- **优点**：不碰 XAML 债；一次写完手机 + 平板 + 别的电脑都能用；改版不用重新发版；
  **完全绕开商店审核**（18+ 内容这条硬约束直接消失）。
- **缺点**：下载落盘在电脑；手机断网即不可用（除非做 Service Worker 缓存已读章节）。
- **适合**：你先要验证"我是不是真的会在手机上看"。

### 方案 2：Avalonia 11（推荐，如果要独立 App）

- **UI 层**：Avalonia 的 XAML 与 WPF 同源，`Tokens.xaml` / `Colors.xaml` 能逐条翻译；
  ViewModel、命令、集合逻辑可以直接复制。但 **WPF 的 `Trigger` / `DataTrigger`、`WindowChrome`、
  `VisualTreeHelper` 用法不通用**，样式要改成 Avalonia 的 selector + classes 写法。
- **播放器**：`FlyleafLib` 是 Windows/DirectX 的，必须换。Android 侧用 `Media3/ExoPlayer`——
  它原生吃 m3u8，短剧那套"实时换签名短链 + 选集连播"反而更简单。
- **下载**：`VideoDownloadService` 依赖外部 `ffmpeg.exe` 做 `-c copy`；
  手机上 `ffmpeg-kit` 已停止维护，选项是自带 arm64 构建（约 20–40MB，注意 GPL）或改用 `Media3 Transformer`。
- **体积**：Avalonia + .NET for Android 的 APK 约 30–50MB（可用裁剪 + AOT 压）。
- **适合**：要一个"装了就能用、能离线、能后台下载"的 App。

### 方案 3：MAUI + Blazor Hybrid

- 一套 Razor 组件 → 手机（WebView）+ 桌面 + 未来的 Web 版。
- 风险集中在 WebView：图片墙、虚拟化滚动、手势（阅读器翻页）都不如原生 XAML 顺手；
  视频仍需原生 handler（`MediaElement` 或自写 ExoPlayer handler）。
- 好处是**方案 1 的 Web UI 可以演进成方案 3 的界面**，不完全浪费。

### 方案 4：原生重写

只有一种情况值得：你打算长期把手机当主战场，并且愿意接受 Core 的 24.8k 行解析逻辑用 Kotlin 再写一遍
（源站一改版就是两处修）。当前项目连 MVVM 都没抽干净，不建议从这里起步。

### 方案 5：薄客户端

手机只做「浏览 + 加入下载队列 + 阅读已同步的书」，下载与刮削全在电脑。
工作量最小，但和方案 1 有 80% 重叠——**做了方案 1 就不必单做方案 5**。

## 5. 推荐路线（分两步，先便宜后昂贵）

### 阶段 0（1–2 天）：抽平台抽象，为两条路共同铺路

在 Core 里把 4 个 Windows 触点收进接口，桌面端行为不变：

| 触点 | 位置 | 接口 |
| --- | --- | --- |
| 数据目录 = `AppContext.BaseDirectory\config`（Android 上 APK 目录只读） | `Core/AppPaths.cs:6` | `IAppPaths` / 由宿主注入根目录 |
| DPAPI 加密密码 | `Core/Services/ConfigService.cs:219,225,247,254` | `ISecretStore`（Android → Keystore） |
| `curl.exe` 子进程过 Cloudflare | `Sources/VideoSources/MissAvSource.cs:520`、`JavDbSource.cs:392`、`Services/VideoScrapeService.cs:344`、`Services/VideoScrape/Fetching/CurlImpersonateClient.cs:40` | `ITlsFetchTransport`（手机侧换 arm64 curl-impersonate 或 uTLS/Cronet） |
| 外部 `ffmpeg.exe` / Shell 缩略图 | `Services/VideoScrape/VideoDownloadService.cs:94`、`Utils/VideoMetadataReader.cs:195`、`Services/VideoThumbnailService.cs:315` | `IMediaToolchain`（手机 → Media3 / MediaMetadataRetriever） |

### 阶段 1（2–4 周）：桌面加 API + 手机 PWA

- 产出：局域网内手机可用的完整客户端，包含 7 个核心页。
- 顺带完成：把 4 个高频页抽成 ViewModel（WPF 侧也受益）。
- **决策点**：用一两周后你会知道手机端真实使用分布——是"看"占 90%，还是"下"占 90%。

### 阶段 2（6–10 周，可选）：Avalonia 独立 App

- 直接吃阶段 1 抽出的 ViewModel 与阶段 0 抽出的接口，重写 XAML 与播放器。
- **Android 先做**：iOS 需要 99 美元/年开发者账号，且 18+ 内容只能自签 / TestFlight 内部，
  单这一条的维护成本就超过收益；iOS 用户给 PWA 即可。

### 不建议的顺序

先做阶段 2 再做阶段 1。原因：36 个视图的迁移一旦开始，
在手机上"到底哪个页面有人用"这个信息你还没有，很容易把 6 周花在没人打开的页面上。

## 6. 手机 MVP 的页面范围（7 页）

| 页面 | 说明 | 桌面端对应 |
| --- | --- | --- |
| 首页 | 继续阅读 / 最近下载 / 源切换 | `MainWindow` 首页区 |
| 搜索 | 聚合搜索 + 结果卡片流 | `SearchView` |
| 详情 | 封面、简介、章节列表、收藏 | `DetailShell` + `ChapterView` |
| 漫画阅读器 | 竖向滚动 / 翻页、预载 3 页、双击缩放 | `ReaderView` / `OnlineReaderView` |
| 小说阅读器 | 翻页、字号、夜间、进度 | `NovelReaderView` |
| 播放器 | 短剧选集 / m3u8 在线播放 | `OnlineVideoPreviewPlayer` |
| 下载 + 本地库 | 队列、暂停、离线列表 | `DownloadPage` + `LocalView` |

**明确不做（第一版）**：视频刮削与演员档案、标签编辑器、设置里的全部高级项、
多窗口 / DWM 圆角、写真图集、排行分类的全部形态。

## 7. 平台适配硬骨头（按风险排序）

1. **Cloudflare / TLS 指纹**：MissAV、JavDB、AirAv 现在靠 `curl.exe` 子进程过被动检测；
   Android 没有 `curl.exe`，必须自带 arm64 curl-impersonate 二进制，或改用能定制 ClientHello 的实现。
   这是唯一可能"做完了但还是拿不到数据"的风险点，**建议先做一天的最小验证**。
2. **ffmpeg**：短剧/视频落盘依赖 `-c copy`。`ffmpeg-kit` 已停止维护，需自编或改 Media3 Transformer。
3. **后台下载**：Android 要前台服务 + 通知（否则进程一挂就断）；iOS 的 `BGTaskScheduler` 只有几分钟窗口，长下载不现实。
4. **存储**：Android 分区存储，下载目录放应用私有目录，导出走 SAF；`DriveLetter` 那套路径配置要作废。
5. **内存**：图片墙与阅读器要按需解码（`BitmapFactory` 采样 / Skia），Core 现在用 ImageSharp 全解码，手机上会 OOM。
6. **播放器替换**：`FlyleafHost` 19 处全部换成 Media3，`OnlineVideoPreviewPlayer` 的宽高比自适应逻辑可以照搬。
7. **UI 线程**：`Dispatcher` 57 处 → Avalonia 的 `Dispatcher.UIThread` 或 MAUI 的 `MainThread`，机械替换。
8. **输入模型**：桌面是鼠标悬停 + 右键菜单（大量 `ContextMenu`），手机要改成点击进入 + 长按菜单。

## 8. 分发与合规

| 渠道 | 可行性 |
| --- | --- |
| Google Play | 不可行：成人内容政策 + 侵权风险，公开上架必被下架 |
| 国内应用商店 | 不可行：需要资质与版号，内容同样过不了 |
| GitHub Releases 侧载 APK | **推荐**：自助下载、自己签名、更新走应用内检查 |
| PWA / 网页 | **推荐**：零审核，`manifest.json` 加到主屏即像 App |
| iOS App Store | 不可行 |
| iOS 自签 / TestFlight 内部 | 技术可行，成本高于收益 |
